# Netarkivet — metadata analysis

An analysis of the metadata for **Netarkivet**, the Danish national web archive run by
the Royal Danish Library. This repository contains the domain inventory of the archive
as it was delivered to us, the list of domains the library could not release, and a
description of what the collection actually contains.

It analyses **metadata only** — one row per archived URL capture, with no page content.
The source export is 170 CSV shards totalling 3.89 TiB in `/work/metadata`; those files
are not part of this repository. All 170 shards were scanned for the numbers below.

## Repository layout

```
├── README.md                     this file: structure + analysis
├── data/
│   ├── domains.txt.gz            every domain in the archive, one per line, sorted
│   ├── domains_stats.tsv.gz      per-domain: records, text bytes, first/last capture
│   ├── top1000_by_records.tsv    the 1,000 largest domains by capture count
│   ├── top1000_by_text.tsv       the 1,000 largest domains by extracted text
│   └── domains_removed.txt       the 2,500 domains the library could not release
├── analysis/
│   ├── summary.json              every number quoted below, machine-readable
│   ├── report.md                 the tables below, as generated by src/report.py
│   ├── per_shard.tsv             per-shard record counts, for spotting a bad shard
│   └── figures/                  the charts below (svg + png)
└── src/
    ├── shardstat.c               single-pass scanner over one shard
    ├── merge.py                  merges per-shard aggregates into data/ + analysis/
    ├── report.py                 renders the tables in this README from summary.json
    ├── figures.py                renders analysis/figures/
    └── run.sh                    the whole pipeline
```

### The data files

`data/domains.txt.gz` is the plain inventory — every distinct domain observed, lowercased
and sorted. `data/domains_stats.tsv.gz` adds the minimum useful statistics per domain:

| column | meaning |
|---|---|
| `domain` | the domain as recorded in the export, lowercased |
| `records` | number of URL captures |
| `text_bytes` | sum of `content_text_length` over those captures |
| `first_capture` | earliest capture date, `YYYYMMDD` |
| `last_capture` | latest capture date, `YYYYMMDD` |

Both are gzipped: uncompressed the domain list alone is past GitHub's 100 MB file limit.
Read them with `zcat`/`zgrep` — no decompression step needed:

```sh
zgrep -x 'dr\.dk' data/domains.txt.gz
zcat data/domains_stats.tsv.gz | awk -F'\t' '$2 > 1000000'
```

### Removed domains

The file `domains_removed.txt` contains 2,500 domains which were declared removed in the
drop sent to us. They are domains whose content can be subject to *offentlig handel* —
public commercial trade — which means the Royal Danish Library is not able to hand them
over to us. As such this list is not an opt-out.

They were removed **before** the export reached us, so the analysis below is of the
filtered archive.

## Source format

Each row of the export is one archived URL capture:

```
"hash","wayback_date","status_code","content_language","domain","url","content_type_full","content_text_length"
```

`hash` is the SHA-1 of the page content, `wayback_date` a `YYYYMMDDhhmmss` timestamp, and
`content_text_length` the byte length of the extracted text. The content itself is not
included — hence `-no-content` in the filenames.

## Analysis

### Headline numbers

| | |
|---|---|
| Records (URL captures) | **18,807,316,668** |
| Unique domains | **6,230,137** |
| Extracted text | **77.08 TB** |
| Distinct content hashes (est.) | 15,612,990,944 (17.0% of records are exact content duplicates) |
| Distinct URLs (est.) | 6,887,250,910 (2.73 captures per URL) |
| Capture period | 1996–2024 |
| Shards scanned | 170 |

The archive is large but far more redundant than the raw record count suggests. Roughly
one record in six is an exact content duplicate of another, and the average URL was
captured nearly three times — so the number of *distinct pages* is materially smaller
than the number of rows.

### Domain concentration

![Cumulative share of records by domain rank](analysis/figures/domain_concentration.png)

The archive has a very long tail: 615,663 domains — 9.9% of the inventory — were
captured exactly once. But the head is less dominant than a web power law usually is.
It takes **18,231 domains to reach half the records**, 221,716 to reach 90%, and just
over a million to reach 99%. The top 100 domains account for only 6.3%. Concentration
is real but gradual, so there is no small blocklist that meaningfully reshapes the
corpus — filtering has to work at the scale of tens of thousands of domains.

The head is also not what you would want from a *Danish* corpus. The largest domains by
volume are dominated by international social media and CDN/asset hosts — `twitter.com`,
`facebook.com`, `youtube.com`, `googletagmanager.com`, `fbcdn.net`, `akamaihd.net`,
`twimg.com`, `gstatic.com`. These are captured because Danish pages embed them, not
because they are Danish content.

![Largest domains by extracted text](analysis/figures/top_domains_by_text.png)

Ranking by text rather than by records makes a second class of outlier visible. The
archive averages 4.0 KiB of extracted text per record, but `googletagmanager.com`
averages 146 KiB, `twimg.com` 281 KiB and `squarespace.com` 251 KiB — scripts,
stylesheets and asset payloads run through a text extractor, not prose.

`bazo.dk` is the clearest case, and it is the second-largest domain in the whole archive
by text: 876.74 GB from 12.6 M captures, 68 KiB each. Sampling the rows shows what it
is — 99% `text/plain` responses from `public.<region>.bazo.dk/v1/articles?…`, the JSON
article API behind the regional TV2 newsrooms, captured once per region. It is real
editorial text, but wrapped in JSON, duplicated across regions, and tagged `en` by the
language detector. Text volume is a better size proxy than record count, but it is not
a proxy for *readable* text, and the largest single contributor is not a web page.

### Language

![Detected content language](analysis/figures/languages.png)

Danish is the plurality but not the whole archive — a large English share (30.4%)
reflects both genuinely English pages on Danish sites and the embedded international
domains above. Note this column is the crawler's *detected* language, not ground truth:
it inherits the detector's error rate, and short pages in particular are detected
unreliably.

### How much text is actually there

![Text length distribution](analysis/figures/text_length_distribution.png)

The distribution is heavily weighted toward short captures: the median record carries
between 1 and 2 KiB of extracted text, and 81% of records carry under 4 KiB. Two hard
edges in the data are worth knowing before using `content_text_length` as a size:

- **No record has between 1 and 63 bytes of text.** The bar at 0 in the chart is not
  short pages, it is exactly the 317,514,079 truncated records described above — the
  count matches to the record. Every record the scanner parsed completely has at least
  64 bytes.
- **No record exceeds 524,287 bytes**, and values pile up immediately below that. The
  upstream extraction caps text at 512 KiB, so the longest pages in the archive are all
  recorded at the same length and their real size is unknown.

### What the records are

Not every record is a successful page fetch. 15.2% of records are not a 200: 12.8% are
404s and a further 2.5% are redirects and other 4xx/5xx responses. Those responses are
archived too and carry a `content_text_length` of their own (error pages have text), so
they inflate naive size estimates. By declared MIME type, 88% of records are HTML or
XHTML, but the tail includes 154 M stylesheets, 83 M JavaScript files and 74 M PDFs.
